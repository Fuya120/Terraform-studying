## 1. プロジェクト概要

### 1.1 背景・目的

#### 背景
当社では、各エンジニアが日々の業務で得た技術的知見（トラブルシューティング手順、ベストプラクティス、環境構築手順等）が個人に属人化しており、以下の問題が発生している。

- **知識の散逸**：退職や異動により、貴重なノウハウが失われる
- **重複調査**：同じ問題に対して複数人が個別に調査を行い、工数が無駄になっている
- **新人教育の非効率**：ナレッジが体系化されておらず、新人が自己学習しにくい
- **情報共有の手段が分散**：Slack、メール、個人メモ等に情報が散在し、検索性が低い

#### 目的
技術的な知見を安全かつ効率的に共有できるWebアプリケーション基盤を構築し、以下を実現する。

1. **知識の資産化**：個人の暗黙知を組織の形式知に転換
2. **業務効率化**：過去の事例を素早く検索でき、調査時間を削減
3. **新人教育の加速**：体系化されたナレッジにより、自己学習を促進
4. **安全な情報共有**：社外秘情報を含むため、セキュアな環境を提供

### 1.2 プロジェクトスコープ

#### スコープ内（今回実施）
- AWS上でのインフラ基盤構築（ネットワーク、サーバ、データベース）
- Terraformによるインフラのコード化
- 高可用性・高セキュリティな3層アーキテクチャの実装
- 基本的な監視・アラート設定

#### スコープ外（今後検討）
- Ansibleによるミドルウェアの自動設定
- Laravelアプリケーションの詳細実装
- ユーザー認証基盤の構築（SSO連携等）
- CI/CDパイプラインの構築

## 2. 業務要件

### 2.1 現状の課題

| 課題 | 詳細 | 影響 |
|---|---|---|
| 知識の属人化 | 個人のPC、個人メモに技術情報が保存されている | 退職時に知識が消失 |
| 検索性の低さ | Slack、メール、Confluenceに情報が散在 | 必要な情報を探すのに時間がかかる（平均30分/件） |
| 情報鮮度の低下 | 古い情報が更新されず残り続ける | 誤った情報に基づいた作業でトラブル発生 |
| セキュリティリスク | 機密情報が個人のクラウドストレージに保存されるケースあり | 情報漏洩リスク |

### 2.2 解決すべき問題

1. **知識の一元管理**  
   技術情報を一箇所に集約し、検索可能にする

2. **情報の鮮度維持**  
   更新日、閲覧数等を可視化し、古い情報を検知

3. **セキュアなアクセス制御**  
   社内ネットワークからのみアクセス可能にする（将来的にはVPN経由も検討）

4. **高可用性の確保**  
   サーバ障害時もサービスを継続できる仕組み

### 2.3 期待される効果

| 指標 | 現状 | 目標（1年後） |
|---|---|---|
| 問題解決時間 | 平均2時間 | 平均30分（75%削減） |
| 情報検索時間 | 平均30分 | 平均5分（83%削減） |
| 新人の自己学習率 | 20% | 70%（先輩への質問頻度を削減） |
| 知識記事数 | 散在（集計不可） | 300件以上（体系化） |

## 3. 機能要件

## 4. 非機能要件

### 4.1 可用性要件

| 項目 | 要件 | 実現方法 |
|---|---|---|
| 稼働率 | 99.5%以上（月間ダウンタイム3.6時間以内） | Multi-AZ構成、Auto Scaling |
| RTO（目標復旧時間） | 1時間以内 | 自動フェイルオーバー |
| RPO（目標復旧時点） | 1時間以内 | RDS自動バックアップ |
| メンテナンス時間 | 月1回、深夜2時間以内 | ローリングデプロイ |

### 4.2 性能要件

| 項目 | 要件 | 実現方法 |
|---|---|---|
| 同時接続ユーザー数 | 100ユーザー | Auto Scaling（最大4台） |
| ページ応答時間 | 平均2秒以内 | ALBによる負荷分散、DBインデックス最適化 |
| 記事検索速度 | 1秒以内 | 全文検索インデックス |
| データベース容量 | 初期20GB、年間成長率50% | RDSストレージ自動拡張 |

### 4.3 セキュリティ要件

| 項目 | 要件 | 実現方法 |
|---|---|---|
| アクセス制御 | 社内ネットワークからのみアクセス可 | セキュリティグループ、ALBリスナールール |
| 通信暗号化 | 全通信をHTTPSで暗号化 | ALBにSSL証明書を設定 |
| データベース暗号化 | DB内のデータを暗号化 | RDS暗号化機能 |
| サーバアクセス | SSHポート開放なし | AWS Systems Manager Session Manager |
| バックアップ暗号化 | バックアップデータも暗号化 | RDS自動バックアップ暗号化 |

### 4.4 運用・保守要件

| 項目 | 要件 | 実現方法 |
|---|---|---|
| バックアップ | 日次自動バックアップ | RDS自動バックアップ（保持期間7日） |
| 監視 | リソース使用率の監視 | CloudWatch Alarms |
| アラート通知 | 異常検知時にメール通知 | SNS経由でメール送信 |
| ログ保持 | 30日間保持 | CloudWatch Logs |
| デプロイ | コマンド1つで環境構築 | Terraform + Ansible |

### 4.5 拡張性要件

| 項目 | 要件 | 実現方法 |
|---|---|---|
| ユーザー数増加 | 将来的に500ユーザーまで対応 | Auto Scaling上限を調整 |
| ストレージ拡張 | データ増加に応じて自動拡張 | RDSストレージ自動スケーリング |
| 環境複製 | ステージング環境を簡単に構築 | Terraformで環境変数を変更するだけ |

## 5. システム構成要件

### 5.1 インフラ要件

| 項目 | 要件 | 詳細 |
|---|---|---|
| クラウドプロバイダ | AWS | 東京リージョン（ap-northeast-1） |
| IaC | Terraform | バージョン1.5以上 |
| アーキテクチャ | 3層構造 | Web層、AP層、DB層を分離 |
| 冗長化 | Multi-AZ | 2つのAvailability Zoneに配置 |

### 5.2 ネットワーク要件

| コンポーネント | 要件 | 詳細 |
|---|---|---|
| VPC | 1つ | CIDR: 10.0.0.0/16 |
| パブリックサブネット | 2つ（Multi-AZ） | ALB、NATインスタンス配置 |
| プライベートサブネット（Web） | 2つ（Multi-AZ） | Nginx配置 |
| プライベートサブネット（AP） | 2つ（Multi-AZ） | Tomcat配置 |
| プライベートサブネット（DB） | 2つ（Multi-AZ） | RDS配置 |
| DNS | Route 53 | 独自ドメイン使用 |
| 負荷分散 | ALB | HTTPSリスナー、ヘルスチェック |

### 5.3 サーバ要件

| 層 | インスタンスタイプ | 台数 | OS | ミドルウェア |
|---|---|---|---|---|
| Web | t3.micro | 2台（Auto Scaling: 1〜4台） | Amazon Linux 2023 | Nginx |
| AP | t3.micro | 2台（Auto Scaling: 1〜4台） | Amazon Linux 2023 | PHP-FPM |
| NAT | t3.nano | 2台（Multi-AZ） | Amazon Linux 2023 | - |

### 5.4 データベース要件

| 項目 | 要件 |
|---|---|
| エンジン | MySQL 8.0 |
| インスタンスタイプ | db.t3.micro |
| ストレージ | 10GB（gp3）、自動拡張有効 |
| Multi-AZ | 有効 |
| 自動バックアップ | 有効（保持期間7日） |
| 暗号化 | 有効 |
| 文字コード | utf8mb4 |

## 7. 前提条件・リスク

### 7.1 前提条件

| 項目 | 前提 |
|---|---|
| AWSアカウント | 既に取得済み、Administrator権限あり |
| ドメイン | Route53で管理済み |
| 開発環境 | Terraform、Ansible、AWS CLIがインストール済み |
| ネットワーク | インターネット接続環境あり |

### 7.2 想定リスクと対策

| リスク | 発生確率 | 影響度 | 対策 |
|---|---|---|---|
| AWSコスト超過 | 中 | 中 | CloudWatchでコストアラート設定、不要リソースは即削除 |
| Terraform状態ファイル消失 | 低 | 高 | S3バックエンドで状態管理、バージョニング有効化 |
| RDS障害によるデータ消失 | 低 | 高 | Multi-AZ構成、自動バックアップ有効化 |
| セキュリティインシデント | 低 | 高 | セキュリティグループ最小権限、Session Manager使用 |
| スキル不足による遅延 | 中 | 中 | 公式ドキュメント参照、コミュニティ活用 |
